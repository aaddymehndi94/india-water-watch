# 19 · Final handoff requirements

The lead produces `state/RELEASE_REPORT.md` using this structure:

## What is actually built

Routes, features, local preview command, tested operating environment, build profiles, ZIP/artifact paths and hashes. No invented deployment URL.

## What the reporting establishes

A small set of fully sourced findings with dates/scopes. Explicitly state whether the evidence supports a national, regional, local or mixed picture. Do not preserve the original “crisis” thesis if the evidence disagrees.

## Evidence and coverage

Source inventory, observation watermarks, geography/metric coverage, historical comparison period, current forecasts and expiry, accepted/withheld claims, corrections to inherited figures and unresolved gaps. Counts are computed, not made up.

## Review status

Automated checks, independent agent review, actual human review, rights/safety checks and not-run items as distinct categories. Link actual artifacts and reviewed snapshot/hash. State blocking versus non-blocking limitations.

## Tests

Exact commands, environment, outputs, screenshots, browser profiles and failed tests fixed. Do not claim a scan establishes complete accuracy or accessibility. Include root/subpath and compact-host tests.

## How to publish

Correct host/profile, required account authorization, current limits, steps, cache/routing configuration and rollback. If already authorized and deployed, include the real verified URL and release ID.

## How to update

The one prompt, exact refresh command, where review candidates appear, how to approve, how to handle blocked feeds and how to add a source. Separate normal content updates from code/dependency changes.

## What remains

Specific human reporting, inaccessible datasets, useful next coverage, maintenance ownership and budget/permission requirements. Do not call a gap-filled prototype the complete national investigation.
